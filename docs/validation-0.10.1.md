# 0.10.1の検証記録

実施日: 2026-09-25。0.10.0の実機導入で見つかった、起動元の環境変数に依存する問題を修正した記録です。公開後にCodexログインまで確認しましたが、実モデルの回答はまだ検証していません。

## 修正と回帰確認

起動元から `PATH` と `Path` を同時に継承すると、.NET Frameworkの `ProcessStartInfo.EnvironmentVariables` が重複キー例外を起こします。セットアップとNative Messagingランチャーでこの辞書を作らず、必要な変数だけをプロセス内で設定するようにしました。Windowsのユーザー・システム環境変数は変更しません。

追加のVM更新検証では、既存の保存フォルダーへ `Set-Acl` を再適用する際に `SeSecurityPrivilege` 不足のエラーを確認しました。これは通常のエクスプローラー起動でも再現します。初回インストールの成功だけでは確認できなかった更新時の問題です。アクセス規則（DACL）の変更だけを保存する `Directory.SetAccessControl` に変更し、監査権限を不要にしました。

ブラウザ検証はPlaywright 1.62.1と、`CHROMIUM_BIN` で指定した既存のChromiumリビジョン1223を使用しました。Playwright既定のリビジョン1234による確認とは区別します。モデルへの要求や利用者の認証情報の使用はありません。

## Windows 11 Home VMでの0.10.0導入

Node.js・CodexがPATHにないWindows 11 Home 25H2とChrome 154で、GitHubの公開Setup.exeをChromeから取得し、公開SHA-256との一致を確認しました。通常のインターネット由来ファイルとしてSmartScreen警告が出ました。利用者が確認して実行しています。

自動操作用に起動したChromeを経由すると、インストール時に上記の重複キー例外が発生しました。Chromeを完全に終了し、同じ公開Setup.exeをエクスプローラーから起動するとインストールは成功しました。すべての通常PCで発生する不具合とは判断していません。

製品用のHKCU Native Messaging登録、固定拡張機能ID、同梱Node.js・Codex、UTF-8マニフェストを確認しました。Microsoftアカウント、Googleアカウント、ホストPCの認証情報は使用していません。

## 0.10.1の更新インストール

最終ビルドのSetup.exeをVMにコピーし、実際に `PATH` と `Path` が重複する起動環境から実行しました。既存の0.10.0への更新が完了し、同梱拡張機能の0.10.1への更新と、保存フォルダーが現在のユーザーとSYSTEMの2者に限定されたままであることを確認しました。追加の管理者権限は要求しませんでした。

確認したSetup.exeのSHA-256は `886ae9130abdd659e4e322987a5174ac25377bc741f6961fe0fdac789a7a0052` です。0.10.1はローカルでビルドしたファイルによる更新検証であり、0.10.0で実施した公開ダウンロード・SmartScreenの検証とは区別します。Chromeの既存の拡張機能登録は削除していません。

## 公開後の確認

0.10.1は[コミットa9e096e](https://github.com/Ringoacid/fast-page-chat/commit/a9e096e)から公開しました。[Source checks](https://github.com/Ringoacid/fast-page-chat/actions/runs/36143280505)と[Publish Pages](https://github.com/Ringoacid/fast-page-chat/actions/runs/36143320301)が成功し、公開アセットのSHA-256と手元の配布物、公開プライバシーポリシーと同梱版の内容が一致することを確認しています。

VMのChromeで補助アプリへの接続、利用者自身によるCodexログイン、モデル一覧の表示を確認しました。一方、Chrome 154の実際のツールバーボタンからパネルを開いてもページを読む一時的な権限が付かず、本文を取得できない問題が見つかりました。このため実回答には進んでいません。対応と以後の確認は[0.10.2の検証記録](validation-0.10.2.md)へ引き継ぎます。
